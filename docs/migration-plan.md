# ShareRide — Migration Plan

Companion to `docs/current-architecture.md`. This is the phased path from the current Vite/React prototype to the production monorepo described in the project brief. Phases are sequential — each should be stable (typechecks, builds, manually verified) before starting the next, per the brief's "do not move to the next milestone with unresolved critical errors" rule.

Implementation is underway — see the "done" markers on individual phases below for what's actually built vs. still planning.

## Guiding constraints (carried from the product brief)

- Passenger = **Ride Request**. Driver = **Ride Offer**. Core product = **Matching**. No seat capacity, ever.
- Business logic (matching, permissions, verification, trip transitions, payment verification, ride expiration) lives server-side only — never trust the client.
- Hyderabad is the seed/demo city, not a hard-coded constraint.
- The existing Vite prototype (`src/`) is the **visual/UX reference**, not throwaway code — its screen structure, copy, and information hierarchy should be preserved as the RN app is built, not redesigned from scratch.

## Phase 0 — Foundation (monorepo scaffold)

Establish, without touching existing app behavior:

```
shareride/
├── apps/mobile   (Expo + React Native + TypeScript, Expo Router)
├── apps/api      (NestJS + Prisma + PostgreSQL/PostGIS)
├── apps/admin    (Next.js + Tailwind + shadcn/ui)
├── packages/types
├── packages/validation
├── packages/api-client
├── packages/config
├── packages/database
├── infrastructure/docker
├── docker-compose.yml   (Postgres+PostGIS, Redis)
├── pnpm-workspace.yaml
└── turbo.json
```

The current `figma-make-app` project (this repo's root) either becomes `apps/mobile`'s design reference kept alongside, or is archived under e.g. `reference/figma-prototype/` once `apps/mobile` reaches screen parity — decide this explicitly before deleting anything.

Deliverables: workspace boots, Docker Compose starts Postgres+PostGIS+Redis, Prisma connects and runs an initial (empty) migration, health endpoint responds, Swagger UI loads, basic CI (install/lint/typecheck) passes on a PR.

## Phase 1 — Domain types & validation packages

Before writing any screen or endpoint, define `packages/types` and `packages/validation` (Zod) for the real domain, replacing the flattened `Ride` type in `src/types.ts`:

- `RideRequest` (passenger side) — fields per brief §13: `id, passengerId, origin, destination, originCoordinates, destinationCoordinates, preferredDate, preferredTimeStart, preferredTimeEnd, preferences, notes, status, createdAt, updatedAt, expiresAt`.
- `RideOffer` (driver side) — per brief §14: `id, driverId, origin, destination, originCoordinates, destinationCoordinates, departureDate, departureTime, stops, preferences, notes, status, createdAt, updatedAt, expiresAt`. **No `seatCount`/`availableSeats`/`selectedSeats`.**
- `Match` — per brief §16, with `matchStatus` in `SUGGESTED | REQUESTED | ACCEPTED | DECLINED | EXPIRED | CANCELLED | CONFIRMED`.
- `Trip`, `TripEvent` — lifecycle per brief §18.
- Carry over what's reusable from `src/types.ts` largely unchanged: `Driver`/`Vehicle` shape (minus `instantBook` living on `Ride` — becomes `autoConfirm`/similar on `RideOffer`), `ChatContact`/`ChatMessage`, `Notification`, `Review`.

This directly resolves the current-architecture finding that `Ride` conflates offer+booking fields with no `Match` concept.

## Phase 2 — Backend skeleton + auth — done (foundation)

- NestJS modules per brief §5 (`auth, users, drivers, passengers, vehicles, rides, matching, trips, chat, notifications, verification, safety, support, payments, admin, analytics, locations, audit, common`).
- Supabase Auth integration; NestJS guards for session verification + RBAC scaffolding (roles table exists, even if only `PASSENGER`/`DRIVER`/`ADMIN` are used initially).
- Verify: passenger login, driver login, admin login, logout, session refresh, at least one protected endpoint.

**What's built:** `apps/api/src/auth` verifies Supabase access tokens via JWKS (no shared secret stored in the API — Supabase's current, non-legacy auth setup), just-in-time-provisions a matching `users` row on first sight, and exposes `GET /auth/me` + `POST /auth/logout` (global `JwtAuthGuard` + `RolesGuard` + `@Public()`/`@Roles()` decorators; `/health` opted out via `@Public()`). Logout revokes that specific access token for its remaining lifetime via a Redis denylist (SHA-256 hash, TTL = time to `exp`) — Supabase JWTs are otherwise stateless and valid until they expire. `apps/mobile` has a working phone-OTP flow (`store/auth-store.ts`, `app/login.tsx`) with the `(tabs)` group redirecting to `/login` when there's no session. `apps/admin` has Supabase SSR (`@supabase/ssr`) with `middleware.ts` protecting all routes and `app/page.tsx` independently checking the `ADMIN` role via the API's `/auth/me` before rendering the dashboard.

Session refresh is handled entirely by the Supabase client SDKs on mobile/admin (that's the standard architecture); the API only ever verifies whatever access token is presented per request, so there's no separate `/auth/refresh` endpoint to build or fake.

**Not verified end-to-end:** this sandbox has no Docker (no live Postgres/Redis) and no real Supabase project, so the full login→API round trip is untested here — verified instead by (a) `pnpm turbo run typecheck`/`lint` passing across all 8 packages, (b) booting the built API and confirming DI wiring resolves correctly up to the point of needing `DATABASE_URL` (expected failure without a live DB), and (c) `next build` succeeding for the admin app. Whoever picks this up next should run `docker compose up -d`, create a real Supabase project, fill in `.env`, and confirm the actual login flow on a device/browser before calling Phase 2 fully closed.

## Phase 12 (pulled forward) — Admin RBAC, Safety/Reports, Audit — done (foundation)

Built ahead of its natural place in the sequence, on explicit request, once real ride/trip/verification tables existed to manage (Phase 1) and the Phase 2 auth plumbing was in place to hang permissions off. Scoped to what could be built as real (Prisma-backed, permission-gated, audited), not mocked:

- **RBAC is real, not the placeholder from Phase 2.** `AdminRoleDefinition` (Prisma) holds the 9 named roles (`SUPER_ADMIN` … `READ_ONLY_ADMIN`) each with a `permissions: String[]` grant, seeded from `packages/types/src/permissions.ts` (`ROLE_PERMISSIONS` — the single source of truth the API guard, seed script, and admin UI all read). `AdminUser.id` is the same id as the corresponding Supabase auth user (mirrors the `User` convention from Phase 2) — `AuthService.syncUserFromClaims` now resolves both tables per request and attaches `admin: { roleKey, roleName, permissions } | null` to `request.user`. `PermissionsGuard` + `@RequirePermission(...)` gate every `/admin/*` route; `apps/admin` reads the same grant via `/auth/me` (`lib/auth.ts`) and hides nav items / disables actions client-side the UI has no permission for (`components/admin-context.tsx`'s `useHasPermission`), while the API independently re-enforces it server-side — the UI check is a UX nicety, not the security boundary.
- **Backend (`apps/api/src/admin`):** `dashboard` (real KPI counts, no placeholder numbers), `users` (list/detail/suspend/reactivate/block/unblock — `AccountStatus` enum replacing the old boolean `isActive`), `drivers` (verification queue: approve/reject/request-info, writes `DriverProfile.verificationNote`), `rides` (requests/offers/matches/trips listing + investigate + cancel-with-audit-trail), `reports` (Safety & Reports: assign/note/resolve/dismiss against the new `Report`/`ReportAction` tables), `roles` (view + edit a role's permission grant), `admin-users` (promote an existing Supabase user to admin, deactivate/reactivate — this is literally how the first real admin gets created, see `packages/database/prisma/seed.ts`'s closing log message). Every mutating action calls the new global `AuditService` (`apps/api/src/common/audit`) — audit logs have no update/delete route anywhere, append-only by construction.
- **Frontend (`apps/admin/app/(admin)`):** Dashboard (wired to the real endpoint, not the old `—` placeholders), Users, Drivers & Verification, Rides (tabbed: requests/offers/matches/trips), Safety & Reports, Roles & Permissions (+ inline admin-account creation), Audit Logs. Shared `DataTable` (TanStack Table) + TanStack Query for all of it; a `PermissionDenied` state renders on direct navigation to a page the signed-in admin's role doesn't grant, even though the sidebar already hides that link.

**Deliberately not built this pass** (schema exists where noted, so nothing downstream has to invent a table under deadline pressure, but no fake UI/endpoints sit on top of an empty feature):
- Notifications template management (create/edit/preview/activate) — `NotificationTemplate` table only.
- App settings management — `AppSetting` table only.
- Verification document viewer (license/vehicle photos/insurance) — no Supabase Storage wiring yet (that's Phase 10 in this plan); `DriverProfile.verificationNote` covers the admin's written reason for now, not a document review UI.
- Bulk actions on the Users table (single-row actions only).
- A separate "Passenger Management" page — passengers are the Users page filtered by type rather than a distinct screen, since the two workflows (view/suspend/block) are identical; Drivers got a dedicated page because verification is a genuinely different workflow.

## Phase 5 — Passenger Ride Requests — done

`apps/api/src/rides` (`RideRequestsController`/`RideRequestsService`, registered in `RidesModule`): `POST /ride-requests`, `GET /ride-requests` (the calling passenger's own, ordered newest first), `GET /ride-requests/:id`, `POST /ride-requests/:id/cancel` — every route scoped to `@CurrentUser()`, a passenger can never see or act on another passenger's requests (same id-not-found response whether the row is missing or just not theirs). Request bodies validate against `packages/validation`'s already-scaffolded `createRideRequestSchema` via a new `ZodValidationPipe` (`apps/api/src/common/validation`) — the first real use of that package. `originCoordinates`/`destinationCoordinates` are PostGIS `geometry(Point,4326)` columns Prisma Client can't touch directly (`Unsupported` type); the service reads/writes them with raw `$executeRaw`/`$queryRaw` (`ST_MakePoint`/`ST_X`/`ST_Y`), the same pattern `packages/database/prisma/seed.ts` already used, merged with the typed Prisma client for every other column. A request's `expiresAt` is a placeholder rule (day after `preferredDate`) until Phase 7's real matching-driven lifecycle exists.

Mobile: `post-ride.tsx`'s passenger flow now calls `POST /ride-requests` on final submit (new `lib/geocoding.ts` resolves typed area names to coordinates via a small Hyderabad lookup table mirroring the seed data, since the wizard has no map picker yet; new `lib/schedule.ts` converts the wizard's free-text date/time labels to the API's ISO date / 24-hour time format) — the driver "Offer a Ride" path stays simulated, since Ride Offers have no endpoint until Phase 6. `my-rides.tsx`'s "Upcoming" tab now fetches real requests via TanStack Query (`useQuery`/`useMutation`, cancel included) instead of `mockData.trips`'s fixture trips; "Completed" and "Offered" stay fixture-backed since matched Trips and Ride Offers aren't real yet.

**A significant side effect of actually verifying this phase**: booting `apps/api` (`nest start` / `node dist/main.js`) had never been tried end-to-end in this environment before — Phases 2/12 were verified via typecheck/build only. Doing so surfaced a real, pre-existing gap: `packages/types`, `packages/validation`, and `packages/database` shipped raw `.ts` source as their package.json `main`/`types`/`exports`, which plain Node (or `nest start`'s compiled output) cannot load — Node's ESM resolver fails on the internal extensionless `export * from './geo'`-style re-exports before even reaching TypeScript-only syntax like `interface`. (A `tsx`-based workaround was tried and rejected: it fixes module resolution but esbuild doesn't fully support `emitDecoratorMetadata`, silently breaking NestJS's constructor-based dependency injection instead.) Fixed properly: all three packages now have a real `tsc` build (`tsconfig.build.json`, CommonJS output, `.d.ts` declarations) and their package.json `main`/`types`/`exports` point at the compiled `dist/`, with `turbo.json`'s existing `dependsOn: ["^build"]` sequencing them before `apps/api`. `packages/config` was left alone — it's config files consumed via `extends`, never imported at runtime.

**Verified**: `pnpm turbo run typecheck lint` clean across all 8 packages; `apps/api` now genuinely boots — `RidesController`'s 4 routes plus every pre-existing auth/admin route map correctly, and it fails only at the real Postgres connection (`P1001: Can't reach database server`), the same class of "expected without live infra" failure Phase 2 documented, just now actually reached instead of assumed. Not run against a live Postgres/Redis/Supabase project.

## Phase 7 — Geospatial matching engine — done

Standalone `apps/api/src/matching` module (`MatchingController`/`Service`, `RouteDistanceService`) — no accept/decline, no Trip creation, that's Phase 8; this only discovers and scores candidates and persists them as `Match` rows:

- **Candidate discovery**: given a `RideRequest`, a PostGIS `ST_DWithin` query (geography cast, 5km radius, on both origin and destination) finds nearby `ACTIVE` `RideOffer`s departing the same date — the "PostGIS proximity queries" the phase calls for. Symmetric in the other direction for a `RideOffer` finding candidate requests.
- **Scoring** (`matching-score.util.ts`, pure functions, zero DB/network — fully unit-tested): `routeCompatibility` = how small the pickup/drop-off detour is relative to the offer's own trip length; `timeCompatibility` = how well the offer's departure sits inside the request's preferred window (linear decay past the edges, 0 on a different date); `proximityScore` = a tie-breaker based on raw pickup/drop-off distance. Combined into one 0–1 score, thresholded into `great`/`good`/`ok` — the exact numbers behind `RideCard.tsx`'s "Great route match" style copy, though the label string itself is a mobile-side presentation concern (like the fixture's existing `matchColors`/`matchLabels`), not something the API returns — `Match` only carries the raw numbers per `packages/types`.
- **Route compatibility distances** come from `RouteDistanceService`, which calls the Google Routes API (`computeRoutes`) when `GOOGLE_MAPS_API_KEY` is configured with that API enabled, falling back to a straight-line-distance estimate (×1.3 road-distance fudge factor) otherwise — same "written for real, not verified against a live key in this sandbox" status as the mobile Maps SDK integration.
- **Persistence**: candidates scoring below `MIN_CANDIDATE_SCORE` (0.25) aren't surfaced at all; surviving ones are upserted as `Match` rows keyed on `(rideRequestId, rideOfferId)` — re-running matching updates the distance/compatibility numbers but never touches `matchStatus`/`expiresAt` once set, so it can't clobber a Phase-8 accept/decline decision later.
- **Endpoints**, matching `packages/api-client`'s already-scaffolded `matchesResource` contract: `GET /ride-requests/:id/matches`, `GET /ride-offers/:id/matches` (added `listForRideOffer` to the client for symmetry), `GET /matches/:id` — every route scoped to the calling passenger/driver's own requests, offers, or matches.
- **Tested against the realistic Hyderabad pair the phase names**: `matching-score.util.spec.ts` (the repo's first real test suite — `apps/api`'s `test` script had no working Jest config until now, fixed alongside this) runs the exact seed coordinates (Madhapur↔Gachibowli request vs Kondapur→Financial District 8:15am offer) through the full scoring pipeline, asserting a well-formed score rather than a specific label — matching `seed.ts`'s own comment that this pair is "not a guaranteed match, left for the matching module to decide."

**Verified**: `pnpm turbo run typecheck lint` clean across all 8 packages; `pnpm turbo run test --filter=@shareride/api` passes (9/9); rebuilt and re-booted `apps/api` — the 3 new routes map correctly alongside every prior route, failing only at the real Postgres connection as expected. No mobile wiring this phase — matches only become actionable (and worth surfacing in the UI) once Phase 8 adds accept/decline.

## Phase 8 — Match acceptance, confirmation, trips — done

`MatchingService`/`Controller` extended with the state machine: `POST /matches/:id/request` (passenger, SUGGESTED → REQUESTED), `POST /matches/:id/accept` (driver, REQUESTED → CONFIRMED), `POST /matches/:id/decline` (driver, REQUESTED → DECLINED). Guard logic lives in pure, unit-tested `match-transitions.util.ts` (`canRequest`/`canAccept`/`canDecline`) — same "extract the pure logic, test it directly" pattern as Phase 7's scoring functions. The schema's `ACCEPTED` enum value is deliberately never written: there's no mobile action between "driver accepts" and "the agreement exists," so accepting jumps straight to `CONFIRMED` in one transaction that also creates the `RideAgreement` and a `Trip` (`scheduledAt` = the offer's departure date+time combined) — this is the "mutual confirmation" the phase brief names: the passenger's `request` and the driver's `accept` together are the two sides of it, there's no separate third confirmation step. That same transaction sets the `RideRequest` to `CONFIRMED` and auto-cancels (not declines — no driver decision was made) any other pending candidate matches for that request, since a passenger only needs one ride. **`RideOffer.status` is deliberately left `ACTIVE`** on accept, not flipped to `MATCHED` — per "no seat capacity, ever," one offer can carry more than one confirmed passenger (the driver decides per request, nothing in the system caps it), so confirming one match must not stop the offer from surfacing as a candidate for others.

`GET /ride-requests/:id/matches` and `GET /ride-offers/:id/matches` now return enriched `MatchWithOfferSummary`/`MatchWithRequestSummary` (new types in `packages/api-client`, which `apps/api` now depends on) instead of a bare `Match` — since `MatchingService` already loads the full `RideOffer`/`RideRequest` server-side to score candidates, returning a summary (driver/passenger name, route, price, schedule) alongside saves the mobile client from N follow-up requests just to show what a candidate even is.

**Mobile — adapted rather than following the literal screen names**: `RideDetailScreen` and Discover's "Requests" tab are both still entirely fixture-driven with no public "browse any offer" endpoint behind them (that's a marketplace-browsing feature no phase has asked for yet — the real discovery path is "post a request, the matching engine suggests candidates," not "browse everything"). Bolting a second, real data path onto `RideDetailScreen` alongside its existing fixture rendering would mean tangled half-fixture/half-real logic in an already-large file, so:
- **Passenger side**: a new screen, `app/matches/[requestId].tsx`, reached via a "View Matches" button added to `my-rides.tsx`'s Upcoming tab (real data, from Phase 5). Lists real candidates via `GET /ride-requests/:id/matches` with a working "Send Request" button per `SUGGESTED` candidate.
- **Driver side**: Discover's "Requests" tab (the actual screen the phase names, and a better fit here since it already existed as a driver-facing tab) now fetches the driver's own real offers, aggregates `REQUESTED` matches across all of them via `GET /ride-offers/:id/matches`, and has working Accept/Decline buttons.
- New `lib/matchLabel.ts` mirrors `matching-score.util.ts`'s exact weights/thresholds client-side, since `Match` carries only raw numbers, not a label — turning them into "Great match"/"Good match"/"Fair match" badges is a presentation concern, same as the fixture data's existing `matchColors`/`matchLabels`.

## Phase 9 — Realtime: WebSockets, chat, notifications — done

Built in two passes. Pass 1 registered the already-scaffolded `RealtimeModule`/`ChatModule`/`NotificationsModule` into `AppModule` and ported mobile's chat/notification screens off fixtures onto the real REST + Socket.IO stack. Pass 2 closed the four gaps that pass left explicit: no notification producers, no durable chat read state, no real conversation entry points, and `expo export` blocked.

**Notification producers** — `MatchingService.request()`/`accept()`/`decline()` and `ChatService.sendMessage()` all call `NotificationsService.create()` now (persist, then realtime-emit — see that method), never a second manual `emitToUser('notification:new', …)`, so there's exactly one emit path. `request()` notifies the driver, `accept()`/`decline()` notify the passenger, a chat message notifies its recipient only — the sender never gets a notification about their own action, verified by dedicated tests (`matching.service.spec.ts`, `chat.service.spec.ts`). **Transaction-safety choice**: `accept()`'s domain change (match/agreement/trip/auto-cancels) is one Prisma `$transaction`; the notification call runs immediately after it resolves, not inside it — wrapping it in the same transaction would mean a failed notification insert rolling back an already-valid trip, the wrong failure mode for what's a secondary concern. `request()`/`decline()` are single Prisma writes to begin with, so the same "notify right after the write succeeds" rule applies trivially. This means a notification-write failure can't corrupt match/trip state, at the cost of a narrow window where the domain change is real but its notification didn't get created — accepted rather than building outbox-pattern infrastructure for it.

**Durable chat read state** — new `ConversationRead` Prisma model (`conversationId, userId, lastReadAt`, additive), one row per member per conversation — deliberately not a per-message `MessageRead` row (this product only needs a per-conversation watermark) and not a `ConversationParticipant` membership table (`Conversation.memberIds` already is that; this only adds a read marker on top of it). `GET /conversations` now returns `unreadCount` per conversation (messages from the other member since `lastReadAt`, or since the conversation's `createdAt` if never read); `POST /conversations/:id/read` (`ChatController.markRead`, identity from the JWT, never a client-supplied id) sets it. Mobile: `app/chat/[id].tsx` calls it once per conversation after messages load; the chat tab badge and Home's conversation list now read the server-backed `unreadCount` (via the shared `['conversations']` TanStack Query cache, patched live by `useChatRealtimeSync.ts` on `message:new`) instead of the old session-only `store/chat-unseen-store.ts`, which is deleted — replaced by a much smaller `store/active-conversation-store.ts` that only tracks which conversation is currently open (so an incoming message for it doesn't bump the badge; `markRead` handles that instead). Read state survives relaunch, logout/login, and a second device, since it's a real table read on every `GET /conversations`.

**Chat authorization tightened** — `ChatService.start()` no longer lets any two users start a conversation; it now requires a real (non-`SUGGESTED`) `Match` connecting the caller and the other user (a `RideRequest.passengerId`/`RideOffer.driverId` pair), enforced server-side (`assertMatched`, `ForbiddenException` otherwise) — chat is scoped to matched participants, not "message any user id you know." `start()` stays idempotent for the normal case (find-then-create, unchanged) — a true concurrent double-tap race could still create two rows, since `memberIds` is a plain array with no DB-level uniqueness constraint over a pair; closing that fully would mean redesigning that column, not undertaken here.

**Conversation entry points** — `app/matches/[requestId].tsx` (passenger, real data) and Discover's "Requests" tab (driver, real data) both got a real "Message" button: `api.chat.start(otherUserId)` (now schema-verified matched, per above) then navigate to `/chat/{conversationId}` — `MatchWithOfferSummary`/`MatchWithRequestSummary` (`packages/api-client`) gained `driverId`/`passengerId` so mobile has an id to call it with. `ride/[id].tsx`, `driver/[id].tsx`, and `ride-tracking.tsx`'s own "Message" buttons are **not** wired the same way and remain a known gap: those three screens are still 100% fixture-driven (no real offer/trip loaded, a pre-existing Phase 8 gap — no public "browse any offer" endpoint exists), so there is no real other-user id on them to resolve a conversation from; fabricating one was explicitly out of bounds. Tapping them lands on the chat screen's real "not available" error state, not a crash.

**Notification navigation** — `Notification.deepLink` (already in the schema, unused before this pass) is now populated server-side on every `notifications.create()` call above (`/matches/:requestId` for match accept/decline, `/(tabs)/discover?tab=requests` for a new match request — `discover.tsx` now reads an optional `?tab=` param — and `/chat/:conversationId` for a message), and `app/notifications/[id].tsx`'s CTA button navigates to it directly. Chose the existing `deepLink` string over adding separate `entityType`/`entityId` columns: it's server-authored only (never client input, so "don't store arbitrary navigation URLs from the client" doesn't apply), and duplicating the same information into two representations would be redundant for what one additive field already does correctly.

**`expo export` fixed** — root cause: `@babel/runtime` is a deep transitive dependency of `expo`/`metro`/`react-native` (confirmed via `pnpm why @babel/runtime -r`) that `@shareride/mobile` never declared directly; pnpm's strict, non-hoisting resolution doesn't expose transitive-only packages, so Metro couldn't resolve `@babel/runtime/helpers/interopRequireDefault` from any file, reproducibly, regardless of this phase's other changes. Separately, the `build` script's bare `expo export` (no `--platform`) defaults to exporting `ios,android,web`, and `react-native-web` was never installed (this app targets Android/iOS only, per its own framing) — fixed by scoping the script to `expo export --platform ios --platform android` rather than adding a web dependency this project doesn't want.

**Database migration**: no `packages/database/prisma/migrations/` directory exists anywhere in this repo — every model added across every phase so far (including this one's `ConversationRead`) has been a `schema.prisma` edit only, never run against a live Postgres. ## Phase 11 — Payments — done

Audited first: the only real price anywhere in the schema is `RideOffer.pricePerPerson` (driver-set, Phase 6) — no platform fee, commission, tax, or discount field exists, and `apps/mobile/app/payment.tsx` (fixture) fabricated both a 5% fee and a flat ₹20 discount client-side. Neither survived into this phase. **Pricing was not blocked**: Trip → RideAgreement → Match → RideOffer.pricePerPerson is a real, already-displayed, driver-authored value — the exact join `TripsService.enrich()` (Phase 10) already does. One Payment per Trip (no seat capacity, ever, applies here too).

**Schema**: `Payment` (`tripId` **`@unique`** — one row per trip for its whole lifecycle, upserted on retry rather than one row per attempt; this unique constraint *is* the idempotency guard), `PaymentRefund`, `PaymentWebhookEvent` (`providerEventId` unique — the idempotency guard for webhook redelivery), `PaymentProvider`/`PaymentStatus` enums. Amount is integer paise throughout, never a float.

**Razorpay integration** — verified against current Razorpay docs (fetched live, not from memory) rather than assumed: order creation via `razorpay.orders.create({amount, currency, receipt})`; checkout-callback verification is HMAC-SHA256(`order_id + "|" + payment_id`, key_secret), via the SDK's own `validatePaymentVerification` utility (confirmed the package ships real first-party TypeScript types, so no `any` or hand-rolled `.d.ts` shim was needed for the server SDK); webhook verification is HMAC-SHA256(**raw** body, webhook_secret) against `X-Razorpay-Signature`, idempotency key is the `X-Razorpay-Event-Id` header. All three live behind `RazorpayService` — nothing else in the codebase imports the SDK, so `PaymentsService`'s 89 unit tests run with zero network calls. `main.ts` now boots with `rawBody: true` so the webhook handler gets the exact bytes Razorpay sent, not a re-serialized parse of them (the docs explicitly warn this can fail signature verification).

**Idempotency & concurrency**: `createOrder()` reads the trip's one `Payment` row and decides — `PAID`/`AUTHORIZED` reject a second charge, an existing `PENDING` order with a `providerOrderId` is handed back unchanged (no second Razorpay order for a repeated tap), `FAILED` gets a fresh order via `upsert`-style update of the same row. `verifyPayment()` is safe to call twice (an already-`PAID` payment short-circuits before touching Razorpay again). Webhook status transitions only ever move toward `PAID`/`FAILED` from `PENDING` (or `PENDING`→`AUTHORIZED`), never backward, so a stale/out-of-order redelivery can't regress an already-settled payment.

**Mobile**: `payment.tsx` rewritten around a real `tripId` (not the fixture's `rideId` — payment only makes sense once a Trip exists, i.e. after match confirmation, not at request time, which the old fixture's pay-at-request flow conflated). New entry point: `(tabs)/my-rides.tsx`'s Upcoming tab now has a "Confirmed trips" section (real Trips, non-terminal status) with a "View / Pay" action — the only place `/payment` is reachable from real data. `ride/[id].tsx`/`driver/[id].tsx`'s old "Pay" buttons still push `/payment?rideId=…` unchanged (same "fixture screen leads to a real screen's graceful empty state, not a crash" treatment as every prior phase's leftover fixture links) — `payment.tsx` now shows "No trip to pay for" rather than reading `rideId` as a `tripId`. Client callback is fast-UX only: on Razorpay Checkout success, the screen shows "Verifying payment…" and only renders success after `POST /payments/verify` returns `PAID` from the server — never from the checkout SDK's own callback alone. Payment status is read from `GET /payments/trip/:tripId` on every mount, not kept solely in React state, so it survives navigation/app restart.

**Expo/native requirement**: `react-native-razorpay` (added to `apps/mobile`, no official types — a local `lib/razorpay-checkout.d.ts` ambient declaration covers the two calls actually used) is a native module. **Confirmed: requires a custom development build (EAS Build with `expo-dev-client`, or `expo prebuild`) — does not run in Expo Go**, which only bundles first-party Expo SDK native modules. `lib/razorpay.ts` wraps the SDK and detects this specific failure mode (`'unavailable'` outcome) so the payment screen shows an honest message instead of crashing or faking success — not testable in this environment (no EAS/native build tooling here).

**Admin**: new `/admin/payments` (list/detail, `payment.read`) and an admin-triggered refund action (`payment.refund`, granted to `FINANCE_ADMIN`/`ADMIN`/`SUPER_ADMIN`), audited like every other admin write. Never exposes a Razorpay secret, webhook signature, or card/UPI instrument detail — the `Payment` model never stores any of those (Razorpay's own PCI-compliant checkout handles them; this API only ever sees ids/amounts/status).

**Explicitly not built, flagged rather than fabricated**: platform fee/commission/tax (no field exists; charges exactly `pricePerPerson`) — needs a product decision before Phase 11 charges anything beyond the raw fare. Driver payout/settlement (Razorpay Route/linked accounts/transfers) — collecting passenger payment is *not* the same problem as paying drivers out, and no wallet/balance was fabricated to paper over that gap. Automatic refund policy — `adminRefund()` initiates a Razorpay refund and records `PaymentRefund`, but there's no `refund.processed` webhook handling yet (not confirmed against current docs in this pass), so `REFUND_PENDING` needs a manual dashboard check until that's added. Cash payments — no cash concept exists anywhere in the schema/UI, so none was added.

Caught one real gap while validating it: `RideRequest`/`RideOffer`'s `originCoordinates`/`destinationCoordinates` geometry columns had no spatial index anywhere in the schema, meaning `MatchingService`'s `ST_DWithin` proximity queries — the core of the matching engine — would sequential-scan every row on every matching run. Added `@@index([...], type: Gist)` on both columns on both models (Prisma's `postgresqlExtensions` preview feature supports this natively) and regenerated the baseline to include the four resulting `CREATE INDEX ... USING GIST` statements.

**Structured logging, request correlation, error handling** — `StructuredLogger` (implements Nest's `LoggerService`, wired via `app.useLogger()` in `main.ts` — redirects every existing `new Logger(X.name)` call site app-wide, no other file touched) emits one JSON line per entry (`timestamp/level/service/environment/context/message` + arbitrary fields), redacting anything matching `/token|secret|signature|password|otp|authorization|apikey|private_?key/i` recursively. `RequestIdMiddleware` reuses a safe incoming `x-request-id` header or generates a UUID (rejects unsafe/oversized values — a log-injection guard). `GlobalExceptionFilter` is the sole place a client-visible error shape is decided (`{statusCode, code, message, requestId}`) — a known `HttpException` (including `ZodValidationPipe`'s own `VALIDATION_ERROR` code) passes its message through, anything else becomes a flat "Something went wrong," the real exception always logged server-side first.

**Health, metrics, provider reliability** — `GET /health/live` (always 200) vs `GET /health/ready` (200/503, checks Postgres `SELECT 1` and Redis `PING` in parallel with a 2s timeout each — Redis is checked because `AuthService.isTokenRevoked` reads it on every authenticated request, so Redis-down is auth-down app-wide; neither leaks a hostname/connection string on failure). `MetricsService` (`prom-client`, chosen over the pre-1.0 `@prometheus-io/client` successor) exposes `shareride_http_request(s)_total/duration_seconds` (route *pattern*, not raw URL, to avoid unbounded label cardinality), `shareride_socket_connections_active`, `shareride_payment_webhook_events_total{event_type,outcome}`, `shareride_matching_run_duration_seconds{for}` — all wired to real call sites, not left as dead declarations: `RealtimeGateway` increments/decrements the socket gauge and logs connection accept/reject/close (reason only, never the JWT); `PaymentsService` increments the webhook counter and logs order-created/verified/verification-failed/webhook-received/duplicate events (safe ids only, never a signature or secret); `MatchingService.findForRideRequest`/`findForRideOffer` are wrapped with the matching-duration timer. `GET /metrics` is `@Public()` with a code comment flagging that production deployment must network-restrict it. Sentry is fully optional — `Sentry.init()` only runs if `SENTRY_DSN` is set, and only 5xx-class errors are captured (a 404/403 domain response isn't an alert-worthy "error").

**Startup env validation** — `ConfigModule.forRoot({validate: validateEnv})` fails fast on a missing `DATABASE_URL`/`SUPABASE_URL` with a specific message, distinguishing required-core vars from optional-provider ones (Razorpay/Redis/Sentry/Google Maps) — never echoes a configured value back in the error.

**Performance/pagination review** — audited every user-facing `findMany` (chat messages, notifications, reviews, support tickets, emergency contacts) plus every admin list endpoint. Admin endpoints already had `page`/`pageSize` pagination via a shared `PaginationQueryDto` (an existing, consistent pattern — no gap). Consumer endpoints are all scoped to "my own X" and naturally small, except one genuine unbounded-growth risk: `ChatService.listMessages` (a long-running matched pair's conversation) had no bound at all. Capped at the most recent 500 (ordered `desc`, reversed for the existing oldest-first response shape) rather than building real cursor pagination — no "load older messages" UI exists yet, so this is a safety bound against an unbounded query, not a new product feature; the response shape is unchanged, non-breaking for the existing mobile client.
